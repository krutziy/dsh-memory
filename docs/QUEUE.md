# 记忆片段与整理队列

> 版本：v0.8 设计（2026-10-21）
> 本文分两部分：**① 大白话**（不用术语讲清整个流程）、**② 技术设计**（实现要用的字段、状态机、迁移）。
> 读不懂技术部分没关系，看第 1 部分就够。

---

## 1. 大白话：这个插件在做什么

### 1.1 一句话

DSH 像一个人：白天经历的事先留下小片段，晚上睡觉时合并成事件片段；
过一周合并成更少的周片段；过一个月合并成更少的长期片段；越久越难想起。

### 1.2 一个具体例子

假设今天是 10 月 21 日（周三）：

| 时间 | 发生了什么 | 插件里留下什么 |
|---|---|---|
| 10:02–10:40 | 你和大肥鱼聊 A 项目的方案，定了三件事 | 一段「10-21 上午 · 事件 1」的小片段，编号 #00041 |
| 14:10–15:00 | 你又来找它聊别的事（新的一次会话） | 另一段「10-21 下午 · 事件 2」的小片段，编号 #00042 |
| 当晚 00:00 后（它空闲了） | 它“睡觉”，把两个事件各自合并 | 两个**事件片段**（更凝练，细节少了），编号仍是 #00041、#00042，等一周 |
| 11 月 1 日夜里（这周结束后第 7 天） | 它把这周所有事件片段合并 | 一段**周片段**，编号 #00050；原来两个事件片段的编号作废 |
| 11 月 30 日夜里（这月结束后第 30 天） | 它把这月的周片段合并 | 一段**长期片段**：不再合并，**也不再有编号** |

之后它回想起来的大概是：“10 月下旬我们定过 A 项目的方案（大概这些要点）”，而不是逐句复述。
时间越久越难想起来；但如果这件事重要、或你后来又提过几次，它就更不容易忘。

### 1.3 四个词

- **片段**：记忆的单位（一段话、一句事实、一张图的概述）。不是聊天记录原文。
- **事件**：一次会话在同一天里的经历。同一天可以有好几个事件。
- **合并**：把若干片段压成更少、更抽象的新片段。合并发生在它睡觉时。
- **编号**：待整理片段在“整理队列”里的临时序号。只在它还等着被合并时存在；
  合并完成、以后不会再压它了，编号就作废回收——片段本身还在，只是不带号了。

### 1.4 为什么这样设计

- 记忆不是录像：细节会淡，抽象会留下；这符合“功能仿生”的原则。
- 会话是“相遇”，不是“记忆容器”：记忆整理完就不属于某次会话了，所以记忆里不需要存会话 id。
- 编号是“待办凭证”不是“永久身份”：所以可以回收，长期运行也不会用光。
- 合并分三层，越往后越抽象：事件 → 周 → 长期；每层固定等 7 天 / 30 天，给人脑式巩固留时间。

## 2. 技术设计

### 2.1 数据流

```
DSH session/event（会话事件）
        │
        ▼
① 记录：每条原始片段写入 Qdrant 前，先确保当天该会话有一个“事件批次”
   → payload { level:0, batch:<编号>, ... }        （编号只在待整理期间存在）
        │
        ▼
② 睡觉（睡眠窗口：默认 00:00，空闲 60 分钟、无运行中会话才进入）
   - 封批：把“今天之前”的收集中的事件批次封存
   - L1：每个事件批次 → 合并成一个事件片段（level=1，batch=事件编号）
   - L2：到期（周结束后 7 天）的事件批次按周合并 → 周片段（level=2，batch=新编号）
   - L3：到期（月结束后 30 天）的周片段按月合并 → 长期片段（level=3，batch 清空、编号回收）
   - 删除被合并的原文/上层片段；维护（去重/过期/索引）
        │
        ▼
③ 回想：按相似度 + 时间新鲜度 + 重要性/复述/置信度动态排序；
   默认不召回最近 10 分钟内自动记录的对话（避免把刚说过的话再注入一遍）
```

### 2.2 事件批次的创建

- 事件键：`(dayKey, sessionId)`。`dayKey` 按用户时区计算，`sessionId` 只用于分组，**不写入记忆 payload**。
- 当天某个会话第一次产生片段时，创建批次：
  - 稳定键 `key = <dayKey>#<seq>`（如 `2026-10-21#01`），永不回收，仅存在于台账与历史；
  - 显示编号 `no = 5 位数字`，顺序分配、完成后回收；
  - 状态 `collecting`，`sessionId` 仅存台账（用于同一会话继续归入同一事件）。
- 手动保存（设置页 / `memory_save`）不属于任何会话：睡眠封批时按天归入 `#misc` 批次统一处理。

### 2.3 批次状态机

```
collecting ──天结束/封批──▶ sealed ──开始整理──▶ running ──成功──▶ waiting（等待下一层到期）
                                                       │                    │
                                                       └──失败──▶ failed ───┘（下个睡眠窗口重试，attempts+1）
                                                       │
waiting ──被下一层合并──▶ merged（编号回收）
L3 成功 ──▶ final（编号回收；产物记忆不带编号）

空批次（没有来源）──▶ merged/final（编号回收，不报错）
```

- `pendingTotal` = collecting + sealed + running + waiting + failed（仍占编号）。
- 编号只在 `final` / `merged` 时回收；回收后同一编号可被新批次使用。
- 稳定键保留在台账历史里，用于追踪血统；不落到记忆上。

### 2.4 批次字段

```js
{
  key: '2026-10-21#01',   // 稳定键（历史追踪用，不回收）
  no: '00041',            // 显示编号（5 位，回收复用）；final/merged 后为 null
  level: 1,               // 该批次产出片段的层级：1/2/3
  status: 'collecting',   // 见 2.3
  dayKey: '2026-10-21',   // L1：事件发生日
  weekKey: '2026-10-19',  // L1/L2：该周周一（用于 L2 合并）
  monthKey: '2026-10',    // L2/L3：所属月份（用于 L3 合并）
  sessionId: '...',       // 仅台账：事件分组用，不写记忆
  createdAt, sealedAt, startedAt, finishedAt,
  dueAt,                  // waiting 时下一层到期时间
  inputCount, outputCount, deleted,
  attempts, lastError,
  sourceKeys: [],         // L2/L3：来源批次稳定键
  fallback, latencyMs, llmCalls,
}
```

### 2.5 压缩链与时间窗

| 层 | 产物 | 输入 | 触发 | 编号 |
|---|---|---|---|---|
| L1 | 事件片段 | 该事件批次的 L0 原文 | 天结束后的第一个睡眠窗口 | 沿用事件批次编号 |
| L2 | 周片段 | 同一周的多个 L1 事件片段（N:1） | 该周结束后 7 天的睡眠窗口 | 新编号 |
| L3 | 长期片段 | 同月的多个 L2 周片段（N:1） | 该月结束后 30 天的睡眠窗口 | 新编号，写完即回收 |

- `anchorTs`：L1=事件当天起点；L2=该周周一零点；L3=该月一号零点（用用户时区）。
- L2 分组键 `weekKey`（ISO 周一）；L3 分组键 `monthKey`（周所属月份 = 该周周一的月份）。
- 同一周/月若因补跑产生多个批次，稳定键追加 `#2` 后缀，仍可被上一层合并。
- 压缩提示词：沿用现有整理提示词；L2/L3 追加一句“这些是同一周/月内多个事件的片段，请合并成更少、更抽象的要点，保留重要事实与偏好”。
- 可选上限（默认关）仍按 40/20/10 生效；模型不可用回退纯规则压缩。

### 2.6 队列持久化与迁移

- 新文件：`$DSH_HOME/storages/dsh-memory/queue.json`
  ```json
  { "version": 2, "lastNo": 123, "batches": [ ... ], "history": [ ... ], "lastRun": {...} }
  ```
- 启动迁移（幂等）：
  1. 若 `queue.json` 存在 → 直接用；
  2. 否则若旧 `consolidation.json` 存在 → 把旧批次转换为新批次：
     - 旧 `pending/processing` → `waiting`，沿用旧 5 位编号（占用中），`weekKey` 由 `dayKey` 推导，`dueAt` 保留；
     - 旧 `done` → `merged`（编号回收）；
     - 旧 `final` → `final`（编号回收）；
     - 旧历史/最近结果复制到新 `history`；
  3. 旧文件保留不删（人工可回退）。
- 旧记忆 payload 兼容：旧字段（`sessionId`/`cwd`）不再读取、不再写入；旧 `batch` 编号若仍对应占用中的批次则保留，否则由维护清理（清空 `batch`）。
- 首次启动时把“没有 batch 的 L0 旧原文”在下次睡眠按天归入 `#misc` 批次处理。

### 2.7 招募/召回变化（v0.8）

- 删除配置：`memoryScope`（global/workspace/session）、`recallIncludeCurrentSession`。
- 新增配置：`recallMinAgeMinutes`（默认 10）——自动召回时排除最近 N 分钟内 `kind=turn` 的自动记录（0 = 关闭）。
  原因：不再靠 sessionId 排除“当前会话”，用时间窗避免重复注入，且对整理后的片段一致生效。
- 记忆 payload 删除 `sessionId`、`cwd`；`batch` 仅表示“当前待整理批次的编号”，固化后为 `''`。
- 工具 `memory_search` 仍全库检索（不套时间窗）。

### 2.8 UI

- 设置页「睡眠整理」下新增**整理队列**视图：
  ```
  流水线：待机 · 睡眠窗口 00:00 · 下次检查 20:15（有会话活动，等待空闲）
  待整理：收集 2 · 待整理 1 · 整理中 0 · 等待合并 3 · 失败 0

  编号    事件         层级  状态      来源→产出  下一步/到期      尝试
  #00041  10-21#01    事件  等待合并   14 → 5     11-01 后合并     0
  #00042  10-21#02    事件  整理中     9 → —      —               0
  #00050  10-19 周    周    等待合并   5 → 2      11-30 后合并     0
  ```
  点击行（或展开）显示失败原因、时间线、血统；历史区显示已合并/已固化的记录（无编号）。
- 术语：L1/L2/L3 在界面上显示为「事件 / 周 / 长期」；「批次」显示为「待整理编号」；
  概览页原「后台队列」改名为「写入队列」（它只是写操作排队，不是记忆队列）。
- 记忆管理页：去掉 cwd 展示；层级徽标改为人话；`#编号` 只在待整理期间显示。

### 2.9 验收标准

- 同一会话同一天的原始片段带同一编号；同一天不同会话得到不同编号。
- 睡眠后：原文消失，事件片段出现且带原编号；编号仍占用。
- 周到期后：事件片段消失，周片段出现且带新编号；旧编号回收（可被新批次复用）。
- 月到期后：周片段消失，长期片段出现且 **不带编号**；台账记录历史、编号回收。
- 重启/长时间不整理：队列状态不丢，到期后补跑；单批失败只影响该批。
- 记忆 payload 中不再出现 `sessionId`/`cwd`；配置页无记忆范围/当前会话选项。
- 旧 `consolidation.json` 可平滑迁移，旧记忆不丢。
